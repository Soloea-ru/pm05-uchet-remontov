# Эксплуатация, качество и рекомендации

Этап 12 индивидуального задания ПМ.05. Коротко: как пользоваться панелью диспетчера СвязьСервис, насколько она годится по критериям этапа 11, какая от неё польза без выдуманных рублей, и что из учебников совпало с этой практикой.

Проверка качества и таблица прогона — в `docs/testing.md`, здесь их не дублируем.

## 1. Как запустить

Нужны Python 3, пакеты из `requirements.txt` и **MySQL 8**. Автотесты MySQL не требуют; живой сайт — требует.

1. Скопируйте `.env.example` в `.env`. Пароль базы и `SECRET_KEY` в git не кладите.
2. Поднимите MySQL:

```powershell
docker compose up -d
```

Compose создаёт базу `svyazservice`, пользователя `svyaz` и подхватывает `sql/schema.sql`, `sql/migration_module3.sql`, `sql/migration_admin_journal.sql`.

Без Docker: создайте базу `utf8mb4`, выполните те же три SQL-файла по порядку, пропишите `MYSQL_*` или `DATABASE_URL` в `.env`.

3. Установите зависимости и запустите сайт:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Откройте http://127.0.0.1:5000

Если база пустая, при старте приложение само добавит справочники и учебные заявки. Если видите страницу «База недоступна» — MySQL не запущен или в `.env` неверные реквизиты.

## 2. Вход и роли

Адрес входа: `/login`.

| Логин | Пароль | Куда попадает |
| --- | --- | --- |
| `admin` | `Admin123!` | `/admin` — все заявки |
| `demo` | `Demo123!` | `/requests` — только свои заявки |
| `maria` | `Maria123!` | `/requests` — только свои заявки |

Новый абонент регистрируется на `/register` (логин латиницей, пароль от 8 символов с буквой и цифрой, ФИО, телефон, email). Роль диспетчера через регистрацию не выдаётся.

Правила:

- без входа `/admin` уводит на `/login`;
- абонент на `/admin`, `/admin/journal` и формы диспетчера получает страницу «Недостаточно прав»;
- неверный логин или пароль: «Неверный логин или пароль.» — какое поле ошибочно, система не говорит;
- «Выйти» очищает сессию; старая ссылка на панель снова требует вход.

## 3. Списки, фильтры, формы

Меню диспетчера: **Все заявки**, **Справочники**, **Журнал**.

### Заявки (`/admin`)

В таблице: номер, дата создания, абонент, адрес и проблема, вариант работ, визит, оплата, статус. На узком экране строки становятся карточками.

Фильтр (поля можно сочетать, кнопка «Показать»):

| Поле | Что отбирает |
| --- | --- |
| Статус | код статуса (`new`, `in_progress`, `done` и ваши записи) |
| Вариант работ | выбранный справочник |
| Поиск | подстрока в адресе, проблеме, ФИО, телефоне или логине |

Пустой результат: «По этому фильтру заявок нет» — это не ошибка. Страниц по 5 заявок, ссылки «Назад / Дальше». Фильтр сохраняется при смене страницы и при смене статуса в таблице.

Статус в строке: выберите значение и «Сохранить» — без отдельной формы.

Полный цикл заявки:

1. «Новая заявка» (`/admin/requests/new`) — абонент, адрес, квартира, телефон, проблема, вариант работ, дата визита, оплата, статус. У диспетчера дата визита может быть в прошлом.
2. «Изменить» — те же поля, уже заполнены.
3. «Удалить» — отдельная страница подтверждения. Отмена возвращает к списку. Восстановления нет.

Ошибки полей (пустой адрес, короткий текст проблемы, неверный телефон) остаются у поля, страница не падает.

### Справочники (`/admin/catalogs`)

Три списка: варианты работ, способы оплаты, статусы.

- «Добавить» / «Изменить»: у работ и оплаты — название; у статуса ещё код (латиница) и порядок (число от 1).
- Удаление с подтверждением. Нельзя удалить запись, на которую ссылаются заявки, и нельзя оставить справочник пустым.

## 4. Журнал

Адрес: `/admin/journal`. Пишет только роль диспетчера.

| Действие | Когда появляется |
| --- | --- |
| Вход | успешный вход `admin` |
| Создание | новая заявка или строка справочника |
| Изменение | правка заявки/справочника и смена статуса в таблице |
| Удаление | подтверждённое удаление заявки или свободного справочника |

В строке: когда, кто (логин), действие, тип записи и номер, краткий текст. Фильтр по действию, страниц по 10 строк. Абонент журнал не видит. Это же данные для анализа использования ИС (кто и что делал), без отдельного файла лога.

## 5. Типовые ошибки

| Что видит человек | Что случилось | Что сделать |
| --- | --- | --- |
| «Неверный логин или пароль.» | Нет такого пользователя или пароль не совпал | Проверить учебную таблицу выше, раскладку |
| «Недостаточно прав» (403) | Абонент открыл URL диспетчера | Выйти и войти как `admin` |
| «Страница не найдена» (404) | Нет такого адреса или заявки | Вернуться на главную, открыть список |
| «Запрос устарел» (400) | POST без CSRF или со старым токеном | Обновить страницу и отправить форму снова |
| «База недоступна» (503) | MySQL не отвечает | `docker compose up -d`, проверить `.env` |
| «Сбой сервера» (500) | Непредвиденная ошибка | Повторить позже; стек Python на экран не выводится |
| Текст под полем формы | Пустое или неверное значение | Исправить поле, не уходя со страницы |
| «Нельзя удалить …: есть заявки» | Справочник занят | Сначала сменить заявки на другую запись |
| «Нужна хотя бы одна запись в справочнике» | Удаляли последнюю строку | Оставить минимум одну |
| «Такое название, код или порядок уже заняты.» | Уникальность справочника | Другое имя или код |

Стек Python пользователю не показывают: все эти случаи идут через `error.html` или сообщение у поля.

## 6. Оценка качества

Критерии и факт прогона — `docs/testing.md` (23 автотеста, 2026-11-13, все пройдены). Кратко по формулировкам бланка:

| Критерий бланка | В этой системе |
| --- | --- |
| Вход только для администратора | Роль `admin`; абонент — 403 |
| CRUD в MySQL | Заявки и справочники через SQLAlchemy; рабочий URI — `mysql+pymysql` |
| Фильтр и пагинация | Список заявок и журнал |
| CSRF | Все POST; без токена — 400 |
| Пароль не открытым текстом | PBKDF2-SHA256 в `users.password_hash` |
| Ошибки | 400/403/404/503 без traceback |
| Журнал действий | Таблица `admin_actions` и экран `/admin/journal` |
| Вывод из базы | Экранирование Jinja2 |

Ограничения честно: автотесты ходят в SQLite, не в живой MySQL; объёма реальной организации нет; это учебный стенд, не промышленный контур.

## 7. Экономическая эффективность (в рамках компетенции)

Ставок, числа заявок в день и стоимости часа диспетчера организация не давала — **рублёвый эффект не считаем**. Ниже только то, что видно из этой практики.

Что экономит время по сравнению с правкой MySQL вручную (консоль, phpMyAdmin):

- смена статуса — одно действие в таблице, без SQL;
- поиск по адресу / ФИО / телефону вместо ручного просмотра всех строк;
- пагинация вместо одной длинной выборки;
- формы с проверкой полей — меньше битых записей, которые потом чинят руками;
- журнал сразу показывает, кто что менял, без разбора бинарных логов СУБД.

Что эффективности не добавляет и чего в расчёт нельзя закладывать:

- учебные данные, не поток реальной компании;
- один диспетчер и локальный Docker, без SLA и резервного копирования;
- лицензий на Flask / SQLAlchemy / учебный MySQL нет, но это не «экономия закупки 1С».

Вывод в компетенции обучающегося: панель снижает ручные операции со справочниками и заявками и даёт след для разбора ошибок. Цифру в рублях без данных профильной организации поставить нельзя — это вопрос к руководителю, если на защите ждут формулу.

## 8. Предложения и рекомендации

### Что из теории пригодилось

- Клиент/сервер, маршруты Flask, шаблоны Jinja2, модели и `config` — как в темах бланка и в пособии Вагина и Петрова: страница собирается на сервере, браузер не ходит в MySQL сам.
- CRUD через ORM, а не сырой SQL в шаблоне; рабочее подключение — MySQL, как требует бланк.
- Сессии, роль, CSRF, хеш пароля, экранирование вывода — без этого панель из бланка не закрывается.
- Три уровня на практике: шаблоны и маршруты (представление), `validators.py` и проверки в `admin.py` (правила), `models.py` (доступ к данным). Жёсткого «сервиса» между ними нет — для этого объёма хватает.
- Журнал закрывает пункт бланка про сбор данных об использовании ИС.

### Чего не хватило в задании и что сделали иначе

- Готовой «чужой» MySQL и отдельной вёрстки админки в бланке нет: взяли схему и экраны СвязьСервис предыдущей практики.
- Пособие Позевалкина и Пановой про клиентские каркасы (React и аналоги) в этом проекте не использовалось: интерфейс — готовый HTML/CSS и немного своего JS, без SPA. Для учебной админки этого достаточно, для «современного фронтенда» из учебника — нет.
- Приложения 1 к презентации в бланке нет: структура слайдов пока черновая (этап 13).
- «Экономическая эффективность» без ставок и объёмов — качественная, не расчёт NPV.

### Что улучшить в админке, если продолжать

1. Вынести учебные пароли со страницы входа: для защиты они удобны, для реальной организации — нет.
2. Резервное копирование MySQL и запуск без `debug=True` — в этой версии это учебный `run.py`.
3. Управление учётными записями диспетчера через панель (сейчас роль `admin` только из seed / базы).
4. Выгрузка журнала (CSV) для разбора за период.
5. Живой прогон автотестов против MySQL, не только SQLite — если руководитель потребует совпадения СУБД теста и работы.
